## 1. 任务一句话概述

用 **TypeScript + 面向对象**方法、与 **AI 智能体协作**，实现一个命令行 REPL 风格的 SVG 编辑器内核：支持 **19 条命令**（文档类 init/read/save/canvas、编辑类 create/delete/move/scale/set/group/ungroup/addto/front/back、显示类 tree/show/help、undo/redo），对 **rect / circle / ellipse / line / text / g** 六种图形做创建、层级组织（`in` / `group` / `addto` 三种归属时机）、容器与叶子的统一变换（Composite 语义）与**一条命令一个单元的 undo/redo**，并能与标准 SVG 文件 **round-trip**（`save` 输出可被浏览器直接打开、`read` 读回外部文件并自动补 id）；作业点明考察重点是「如何与 AI 一起完成一个架构良好，恰当使用了设计模式的应用」（原文 L96），交付物为远程 git 仓库（分步提交历史 + 截止前打 `final` tag）与工程内 `doc/README.md`（含架构方案、过程记录、一致性自查、质量保证手段四节）（L100–L130）。

## 2. 任务展开：需求、意图与能力培养

### 2.1 任务需求的具体形态

- **一个 REPL**：提示符 `svg>`，逐行读入命令，`#` 开头行为注释——因此命令序列可以存成脚本回放（L141）。
- **一棵图形树**：六种图形类型加 `<g>` 容器构成树形文档模型；所有命令**一律按唯一、大小写敏感的 id 定位**（L142），读入外部 SVG 缺 id 时按「标签名+序号」自动补并打印警告（L143）。
- **两类命令语义**：文档类（init/read/save/canvas 改尺寸）与文件/画布相关，执行后 **undo/redo 禁止**（L162、L251）；编辑类命令全部可 undo/redo，且**一条编辑命令 = 一个 undo 单元**（L250）；显示类不进 undo 栈（L185）。
- **文件 round-trip**：`save` 产出的就是标准 SVG（可直接在浏览器打开预览，L9–L10）；`read` 读回外部 SVG（L167）。复合图形 box 的序列化/读回降级策略（`data-kind` 标记）已为插件阶段预定义（L291）。
- **阶段边界**：`box` 复合类型属于**后续插件化阶段**的目标，本阶段 `create box` 报 `unknown shape type`（L175、L255）；但错误文案 `(is the plugin loaded?)`（L240）与「变化点假设」要求（L114）都暗示本阶段架构**要为插件留好插槽**。

### 2.2 命题意图（为什么这么考）

原文开宗明义：「本Pj考察的重点是**如何与AI一起完成一个架构良好，恰当使用了设计模式的应用**」（L96）。拆开是三层：

1. **AI 协作工程**：作业把「使用 AI 智能体（Codex、Qoder 等）协作完成」写进实现范式（L157），又在文档要求里专设「过程记录」——记录「你从 AI 给的建议、生成的文档或代码中发现了什么问题、如何确认并纠正」（L118）。意图是训练「把 AI 当执行者、自己当架构师与验收者」的工作方式：出方案、定规范、审产出。
2. **架构与演进意识**：架构方案的四项要求里，「依赖方向规则」与「变化点假设」（L113–L114）明确针对一次性堆代码；作业还预埋了至少三个已知变化点——`box` 插件类型（L253–L293）、「CLI / agent / 鼠标三种通道」的提法（L149，暗示后续有鼠标 GUI 与 agent 阶段）、文件名 `phase_cli_1` 本身（CLI 阶段第一步）。
3. **设计模式落地**：undo/redo 事实上强制 **Command**（L112 明写「要求使用Command模式」）；容器与叶子统一操作强制 **Composite**（L156）；「按名字分派只允许两处：命令分发与图形工厂」（L155）是对 **Factory** 位置的精确约束；`(is the plugin loaded?)`（L240）预告开闭原则与插件化。

### 2.3 培养/锻炼的能力

- **面向对象建模**：树形领域模型（图形类层次、摘出/提升/保序等树操作、id 索引）。
- **设计模式的选择与落地**：Command、Composite、Factory 为必答，undo 的实现路线（逆命令 vs 快照）是真实的模式权衡。
- **架构文档能力**：模块划分 + PlantUML 组件图/包图、依赖方向规则、变化点清单（L111–L114）。
- **演进式设计**：为插件化与多通道（GUI/agent）预留插槽而不实现（L114、L149、L255）。
- **质量保证意识**：端到端 transcript 验收（§6）、错误路径覆盖（§4.2）、一致性自查（L121–L127）。
- **AI 产出批判性审查**：过程记录要求写出发现的问题与纠正过程（L118）。
- **Git 工程习惯**：分步提交、禁止 one-shot、tag 管理（L100）。

### 3.3 从原文可推导的细节（未明说、可推断，需在设计时确认）

1. **save 的元素计数不含 `<svg>` 根**：demo.svg 计 5 = bg + title + g#markers + c1 + box（L373）；other.svg 计 7 = 全部非根元素（L379）；flowchart.svg 计 8 = flowchart + node1 + 2×(rect+text) + arrow1（L474）。三例一致：**计数 = 除根外全部元素（含 g）**。
2. **move 的回显格式分两种**：叶子报绝对位置 `circle#c1 moved to (130,100)`（L354），undo 为 `moved back to (100,100)`（L356）；容器报增量 `g#node2 moved by (0,100)`（L465），undo 为 `moved back by (0,-100)`（L467）。
3. **delete 的 undo 回显**：`rect#box restored into g#markers`（L370）——恢复回**原父容器**。
4. **tree 每类型的属性格式**：rect `x= y= w= h= fill=`；circle `cx= cy= r=`；text `(x,y) "内容"`；line `(x1,y1) -> (x2,y2)`（L306–L310、L457–L462）。
5. **ungroup 的两种拒绝与本阶段的可行性**：普通 `g` 可以 ungroup（L181 是本阶段命令）；但「复合图形」（插件类型，本阶段不存在，L241）与「根级容器」（svg 直接子节点，L243）不可 ungroup。
6. **`#` 注释仅识别行首**（L141），因此 text 内容含 `#` 不受影响（但需自定引号内 `#` 的解析规则，见 Q7）。
7. **启动 banner**：`svg-editor 0.1 — type 'help' for commands`（L330）。

### 4.2 需要抉择的架构与技术选型

1. **undo/redo 实现路线**（影响最大的抉择）：
   - *逆命令*：每个 Command 实现 do/undo，redo 即再 do——语义直观，但每个命令写两套逻辑，容器操作（group/ungroup/scale 递归）的逆操作易错；
   - *快照/Memento*：命令执行前拍（路径级）快照——实现省力、天然正确，但要控制快照粒度与内存。
   - 无论哪条路，必须与 Command 模式自洽（L112）。**倾向：逆命令为主，仅 delete 这类大改动考虑快照兜底**——最终以架构文档论证为准。
2. **容器变换的内部表示**：move/scale 容器时，是「扁平化」（直接改写每个子孙坐标）还是「g 存 transform、渲染时合成」？影响 ungroup 的「占据原容器的位置」（L181）、save 是否输出 `transform` 属性、以及读入外部带 transform 的 `<g>`（原文背景知识专门演示了 transform，L52–L66）的 round-trip。**倾向：内部扁平化坐标（本阶段最小正确实现），外部 transform 读入时展开**，并把该假设写入架构文档。
3. **XML 解析：手写 vs 库**（如 fast-xml-parser / @xmldom/xmldom）：手写可控 round-trip 细节与警告注入；库省力但丢原始格式。作业点名「IO 未隔离」属架构层问题（L154），即 IO 必须隔离成独立模块。**倾向：手写小解析器**（本阶段只需 6 种元素 + svg 的子集），属性保真更可控。
4. **模块划分草案**（架构方案起点，非结论）：`cli`（REPL、词法/参数解析）→ `command`（命令对象、分发表、undo 栈）→ `core`（Shape 类层次、Document、id 注册表）→ `io`（SVG 读写）→ `render`（tree/show 文本渲染）→ `factory`（类型注册，为 ShapeProvider 插槽预留）。依赖方向：core 不依赖 command/cli/io；io、render 单向依赖 core；command 经接口依赖 core。
5. **测试框架**：Vitest（或 Jest）；把 §6 transcript 直接做成端到端断言，§4.2 错误表逐条单测——这同时就是 A11「质量保证手段」的答案。
6. **运行形态**：Node + npm，入口 `npm run cli`（L329）；需定 Node 版本与 ESM/CJS。
7. **AI 协作流程**：先固化架构文档与「命令-行为-文案」规范表，再让 AI 按模块实现，人对每个模块做一致性检查——直接服务 A9/A10 的交付要求。
